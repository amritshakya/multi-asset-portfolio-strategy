# Methodology Audit

This document records the forensic findings on the **original** implementation
of this project (`archive/original-final.Rmd`, `paper/final-paper.pdf`, and
the "corrected" standalone script `code/portfolio-analysis.R`). It is a
historical record, not a live spec — none of these three files were altered
as part of this audit or the Stage 1 rebuild. The rebuild's own methodology
lives in a separate document: [`docs/rebuilt-methodology.md`](rebuilt-methodology.md).

All findings below were verified empirically (not just read from source) by
running the actual code in this repository, including live data downloads,
during the audit session that preceded Stage 1.

## Summary of established problems

1. **Headline results were generated in-sample.** `optimize.portfolio()` was
   handed the complete 2016–2025 monthly return history and asked to choose
   weights; that same weight vector's performance was then reported as the
   fund's "historical performance," evaluated on the very data used to choose
   it. Training window and evaluation window were identical (100% overlap).
   Reproduced numbers for this static, in-sample portfolio: **CAGR 33.2%,
   annualized vol 40.3%, max drawdown 59.8%.**

2. **The static portfolio was never periodically rebalanced.**
   `Return.portfolio(R, weights = new_weights)` was called with no
   `rebalance_on` argument, which makes it a buy-and-hold position that
   drifts with realized returns rather than a maintained target allocation.

3. **BTC drifted to roughly 68.5% of the realized portfolio** by the end of
   the sample (starting from a nominal 5% target), directly because of (2).
   The single risk control the entire narrative was built around — "a strict
   5% allocation cap... limits overall portfolio risk" — did not describe the
   portfolio whose returns were actually being measured for most of the
   10-year window.

4. **The archived paper's CAPM regression used the annual 4.5% risk-free
   assumption as if it were a monthly rate**, subtracting roughly 12x too
   much from monthly excess returns. Verified algebraically and numerically:
   this materially inflates the reported annualized alpha (0.429 in
   `paper/final-paper.pdf`) relative to what a correctly unit-converted
   monthly risk-free rate produces (0.177, as computed by
   `code/portfolio-analysis.R`, which does convert correctly).

5. **Reported risk contributions (MCR/CR/PCR) described the static target
   weights, not the drifting portfolio that generated the returns.** By the
   time BTC had drifted to ~68.5% of the book, the risk-budget table still
   showed BTC at its original 5% target weight.

6. **A legitimate walk-forward routine existed in the same script but was
   never used for any headline statistic.** `optimize.portfolio.rebalancing()`
   with a 24-month training/rolling window produced a genuinely
   look-ahead-free backtest (`bt_ret`), which was plotted once (as an equity
   curve) and then discarded — none of its CAGR, volatility, Sharpe, or
   drawdown numbers were ever tabulated or reported. Reproduced numbers for
   that walk-forward series: **CAGR 19.2%, annualized vol 19.5%, max drawdown
   15.4%** — roughly a quarter of the headline drawdown and half the
   volatility of the in-sample number from point (1).

7. **No transaction costs or turnover were modeled anywhere**, despite the
   walk-forward weights swinging by 20–40 percentage points between adjacent
   monthly rebalances.

## Additional findings from the same audit (for completeness)

| Ref | Finding | Severity |
|---|---|---|
| H2 | Max drawdown computed from month-end returns only, understating true intra-month drawdown for a BTC-heavy book | High |
| H4 | `IntroCompFinR` (efficient-frontier plotting dependency) is not on CRAN and undocumented — blocks a new clone | High |
| M1 | `na.omit(Return.calculate(monthlyPrices), method = "log")` in the archived Rmd silently binds `method` to `na.omit()`, not `Return.calculate()` — returns are actually discrete, not log, despite the comment | Medium |
| M2 | Estimation-error instability: 24 monthly observations to estimate 20 free parameters (5 means + 15 covariance terms) for a 5-asset optimizer | Medium |
| M3 | Original Sharpe ratio formula mixed a geometric CAGR numerator with an i.i.d.-annualized volatility denominator | Medium |
| M4 | README/executive-summary numbers were hand-transcribed, not generated by any script | Medium |
| M5 | `add.objective(type="return", name="mean")` + `add.objective(type="risk", name="StdDev")` carries an implicit, undocumented risk-aversion default — see `docs/rebuilt-methodology.md` section 6 for the full diagnosis | Medium |
| M6 | Merging all assets into one `xts` object before calling `to.monthly()` silently reconciles BTC's 7-day trading calendar down to the last row with no missing values across *any* column — i.e. equities' calendar quietly wins | Medium (fixed in Stage 1, see `R/returns.R`) |
| L1–L4 | i.i.d. bootstrap on a non-stationary series; selective YTD framing; stray untracked files; no package/version pinning | Low |

## What this means for the rebuild

The Stage 1 rebuild (see `docs/rebuilt-methodology.md`) directly addresses
items 1–3, 5, 6, and 7 above by construction (explicit walk-forward timing,
enforced monthly rebalancing with tracked drift, per-asset calendar
alignment, and an explicit transaction-cost model). Item 4 does not recur in
Stage 1 because CAPM/alpha is not a Stage 1 deliverable. Item M5's
objective-function ambiguity was resolved by directly inspecting the
PortfolioAnalytics source and reproducing the underlying mathematical
program transparently, outside the package's implicit defaults — see
`R/optimizer.R` and `docs/rebuilt-methodology.md` section 6.

**The old headline performance numbers (33.2% CAGR / 59.8% drawdown) are not
targets.** They are reconciliation references only, retained to show how
much of the original project's apparent outperformance was a methodology
artifact rather than a property of the underlying assets or strategy idea.
